# Telegram 频道资讯监测平台：公共前台与管理后台设计

日期：2026-07-14

## 1. 背景与问题

当前系统把来源状态、消息时间线、告警规则和投递状态放在同一套受保护界面中。所有访问者首先看到管理密钥输入框，无法作为公共资讯站使用；同时，产品名称“安全告警台”与当前监测的公开资讯频道不一致。

现网还存在两个可复现的体验问题：

- 图片使用固定 `16:10` 或 `16:9` 比例以及 `object-fit: cover`，导致图片被放大、裁切，信息显示不完整。
- 分组筛选时旧结果继续停留，切换完成前缺少明确反馈；新结果显示后又同时加载多张原图，造成“查询很慢”的感受。

生产测量显示 SQLite 分组查询中位数约为 `0.24ms`，HTTPS 消息接口通常为 `40–136ms`。因此当前筛选瓶颈不在数据库，首要优化对象是筛选状态管理、结果缓存和媒体加载。

## 2. 目标

- 建立免密、只读的公共资讯前台。
- 新建独立的单管理员管理后台。
- 允许管理员管理来源、公开范围、采集状态、消息和监测规则。
- 将产品定位调整为公开 Telegram 频道内容聚合与监测。
- 完整显示图片，降低媒体加载对筛选体验的影响。
- 移除企业微信相关 UI 和运行任务。
- 保留现有 SQLite 数据，采用增量迁移并维持单机部署。

## 3. 非目标

- 不增加用户注册、用户列表、角色权限或多管理员体系。
- 不接入企业微信、邮件、短信或其他通知通道。
- 不迁移到 PostgreSQL、Redis、对象存储或微服务。
- 不开放服务器配置、环境变量或密钥的网页编辑能力。
- 不支持任意正则表达式或通用规则脚本。

## 4. 架构决策

采用“模块化单体”架构：

- 公共前台位于 `/`。
- 管理后台位于 `/admin`。
- 两者使用独立的前端入口和生产构建产物，共享基础组件与类型。
- FastAPI 按公共 API、管理 API、领域服务拆分模块。
- 消息、来源、媒体、监测规则与采集健康使用共享领域服务。
- SQLite 继续作为唯一数据库。
- 采集调度继续运行在当前应用容器内。
- Caddy 继续作为 HTTPS 反向代理，应用端口保持仅监听 `127.0.0.1:8000`。

当来源数量、持续写入并发或数据库规模明显超过单进程能力后，再评估拆分采集 Worker、PostgreSQL 和 Redis。当前 4GB VPS 和两条来源不具备拆分收益。

## 5. 产品命名与入口

### 5.1 公共前台

- 名称：`Telegram 频道资讯监测平台`
- 说明：`公开频道内容聚合、检索与状态追踪`
- 入口：`/`
- 不显示密钥输入框。
- 页面右上角提供低强调度的“管理员入口”，跳转至 `/admin`。

### 5.2 管理后台

- 名称：`频道监测管理中心`
- 入口：`/admin`
- 未登录时显示管理密钥登录页。
- 登录成功后进入运行概览。
- 导航包含：运行概览、来源管理、消息检索、监测规则、命中记录、系统状态。

产品文案统一使用“监测规则”和“命中记录”，避免在来源不具备安全属性时使用“安全告警”描述。

## 6. 数据模型与迁移

新增 `sources` 表，作为运行时来源的唯一事实来源：

- `chat_id`：主键，沿用当前稳定来源 ID。
- `name`：显示名称。
- `source_url`：Telegram 公开频道 URL。
- `source_type`：首版固定支持 `telegram_public`。
- `enabled`：是否参与采集。
- `public_visible`：是否允许公共前台和公共 API 访问。
- `created_at`、`updated_at`：审计时间。

新增来源时只接受可规范化的 Telegram 公开频道 URL，并由服务端稳定派生 `chat_id`；首版不允许直接修改来源 URL，避免来源身份与历史消息错配。

迁移规则：

1. 启动时检测 `sources` 表是否为空。
2. 若为空，从现有 `config/groups.yaml` 幂等导入来源。
3. 当前已有两个来源迁移后设置为 `enabled=true`、`public_visible=true`。
4. 后续通过管理后台新增的来源默认 `enabled=true`、`public_visible=false`。
5. YAML 在首个兼容版本中仅作为一次性种子和回滚参考，不再作为运行时配置来源。
6. 不删除已有消息、来源运行记录、规则或历史投递表。

## 7. API 边界

### 7.1 公共 API

公共 API 不要求管理员会话，并且只能访问 `enabled=true` 且 `public_visible=true` 的来源：

- `GET /api/public/sources`
- `GET /api/public/messages`
- `GET /api/public/media/{message_id}/{index}?variant=thumbnail|original`

公共来源响应只包含显示名称、来源链接、消息数量和简化后的活跃状态；不返回原始采集错误、内部文件路径、调度配置或待处理数量。

公共消息响应继续移除 `raw_json`、原始媒体地址、服务器路径和内部投递字段。公共媒体接口在返回文件前必须验证消息所属来源仍然公开。

### 7.2 管理 API

管理 API 继续要求 12 小时 `HttpOnly + Secure + SameSite=Strict` 会话 Cookie。所有状态变更接口同时校验同源请求：

- `GET/POST /api/admin/sources`
- `PATCH /api/admin/sources/{chat_id}`
- `GET /api/admin/messages`
- `GET /api/admin/operations/summary`
- `GET/POST /api/admin/rules`
- `PATCH /api/admin/rules/{id}`
- `GET /api/admin/matches`
- `POST /api/admin/matches/{id}/acknowledge`
- `POST /api/admin/matches/{id}/resolve`
- `POST /api/admin/sources/{chat_id}/crawl-now`

登录与退出继续使用 `/api/auth/login`、`/api/session` 和 `/api/auth/logout`。

旧的受保护消息、来源与规则接口在一个兼容版本内保留，前端不再调用；确认新入口稳定后再单独移除。

## 8. 公共前台交互

桌面采用“来源侧栏 + 消息主栏”，移动端使用单列消息和筛选抽屉。公共前台不显示采集错误、投递状态、告警处置按钮或内部运行指标。

筛选行为：

- 来源点击后立即提交，不要求再次点击“应用筛选”。
- 关键词和媒体类型保持显式提交，避免每次输入都请求服务器。
- 使用 `AbortController` 取消旧请求。
- 使用筛选键保存短期内存缓存；切回已访问筛选时先显示缓存，再后台重新验证。
- 无缓存时立即清空不匹配的旧分组并显示对应骨架屏。
- 工具栏显示当前来源和明确的加载状态。
- URL 保留来源、媒体类型和关键词，支持深链、前进与后退。
- 页面隐藏时停止轮询。

首屏默认读取 20 条消息，后续使用游标分页。公共列表 API 使用 ETag 和 `no-cache` 进行低成本重新验证，管理 API 与管理媒体继续使用私有、不缓存策略。前端内存缓存只用于即时切换，并在后台请求完成后更新；服务端对每次新请求重新校验公开范围。

## 9. 图片与媒体

列表图片不再使用固定比例裁切：

- `object-fit: contain`
- 宽度不超过消息卡片。
- 高度按原始比例计算，并设置合理最大高度。
- 图片背景使用中性深色，避免透明区域或窄图难以辨认。
- 点击图片打开可键盘关闭的查看器，展示原图。
- 视频封面也使用完整比例显示，不再强制裁切。

服务器为公开图片生成保留比例的缓存缩略图，限制最长边与输出体积；列表加载缩略图，查看器再请求原图。缩略图失败时回退到原图或 Telegram 原文，不阻塞消息文本渲染。

音频、视频、文件继续使用各自语义控件。所有媒体失败状态提供原文链接和可访问说明。

## 10. 管理后台功能

### 10.1 运行概览

- 来源总数、公开来源数、今日新增消息、待处理命中数量。
- 每个来源的健康状态、最近成功采集、抓取数、入库数和最近错误摘要。

### 10.2 来源管理

- 新增 Telegram 公开频道 URL。
- 修改显示名称。
- 启用或停用采集。
- 控制公共可见性。
- 手动触发单个来源采集。
- 删除操作首版不提供；停用来源可避免误删历史数据。
- 来源 URL 首版不可修改；需要更换频道时新增来源并停用旧来源。

### 10.3 消息检索

- 支持来源、媒体类型、关键词和时间范围。
- 只读查看消息和媒体，不允许修改采集内容。

### 10.4 监测规则与命中记录

- 继续支持来源、普通关键词、媒体类型、免打扰时段、冷却时间和启用状态。
- 规则默认禁用。
- 命中状态保持“新命中、已确认、已解决”。
- 不提供企业微信或其他通知投递配置。

## 11. 移除企业微信链路

- 前端删除投递列表、失败重试、待投递数量和“已投递/待投递”文案。
- 调度器不再注册定时转发与投递重试任务。
- 新消息入库不再创建 `delivery_batches`、`delivery_items` 或 `delivery_attempts`。
- `forwarded_at` 不再作为产品状态展示或新流程判断依据。
- 已有投递表、日志和字段暂时保留，只用于历史兼容和回滚，不再写入。
- 企业微信客户端和旧投递代码在兼容版本中保留为未引用代码，稳定观察后再单独清理。

## 12. 错误处理与可观测性

- 公共端错误使用不泄露内部细节的提示，并允许就地重试。
- 管理端区分来源、消息、规则和系统错误。
- 来源错误继续做服务器路径脱敏。
- 公共媒体失败不阻塞消息文本。
- 来源配置变更、手动采集和规则状态变更记录结构化日志。
- 公开范围变更立即影响后续公共 API 请求；不依赖服务重启。已经发送到浏览器并正在显示的内容只能在下一次重新验证或刷新后移除。

## 13. 安全边界

- 管理密钥永不下发到公共前端构建产物。
- `/admin` 未认证时只返回登录界面，不预取管理数据。
- 公共 API 按数据库中的公开来源做服务端过滤，不能依赖前端隐藏。
- 公共媒体接口再次校验来源可见性，防止通过已知消息 ID 绕过。
- 管理状态变更继续要求会话和同源校验。
- CSP、禁止嵌入、MIME 嗅探防护和 localhost 端口绑定保持不变。

## 14. 测试与验收

后端测试覆盖：

- YAML 到 `sources` 的幂等迁移。
- 新来源默认不公开。
- 公共 API 只返回公开来源和对应消息。
- 公共媒体无法读取未公开来源。
- 管理来源增改、停用、公开切换和手动采集。
- 企业微信调度任务不再注册，新消息不再创建投递批次。
- 管理接口鉴权与同源校验。

前端测试覆盖：

- 公共入口不显示密钥输入框。
- `/admin` 未登录显示管理登录页。
- 来源切换立即进入正确的加载或缓存状态。
- 旧请求无法覆盖新筛选结果。
- 缓存命中先显示结果并后台刷新。
- 图片使用完整比例，并能打开、键盘关闭查看器。
- 公共端不显示管理指标和企业微信内容。

E2E 固定验证 `1440×900`、`768×1024`、`390×844`：

- 公共首页免密加载。
- 来源切换、关键词筛选和 URL 前进后退。
- 图片无裁切、无横向溢出、查看器可操作。
- 管理登录、来源公开开关和规则状态变更。
- 减少动态效果和键盘操作。

发布验收：

- 备份 SQLite 与 `data/`。
- 增量创建 `sources` 表并导入现有来源。
- 两个现有来源在公共首页可见。
- `/admin` 才显示管理登录。
- 企业微信任务未注册且后台无相关入口。
- 生产来源持续采集，公共 API 不暴露内部字段。
- 裸 IP 的 8000 端口继续不可访问。

## 15. 已确认决策

- 架构：模块化单体。
- 公共范围：仅管理员标记公开的来源。
- 管理模式：单管理员密钥，不做 RBAC。
- 企业微信：从 UI 和运行链路移除，历史表保留。
- 公共名称：Telegram 频道资讯监测平台。
- 管理名称：频道监测管理中心。
- 数据库与部署：继续 SQLite、FastAPI、单容器和 Caddy。
